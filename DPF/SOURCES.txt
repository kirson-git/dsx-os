Explicit renderer adaptations:
- Helm template includes chart CRDs. Argo uses server-side apply and explicit
  resource sync waves. Namespaced resources have explicit metadata.namespace.
- Kamaji replicaCount=2 uses the actual chart key. The upstream values spell
  replicas: 2, which the pinned chart does not read.
- Kamaji defaultDatastoreName is empty, preventing its default-datastore admission
  bootstrap dependency. The named default DataStore is created at wave 32.
  DPF 26.4.0 explicitly sets dataStore: default on its TenantControlPlane requests:
  https://github.com/NVIDIA/doca-platform/blob/v26.4.0/internal/clustermanager/kamaji/handler.go
- Kamaji etcd PVCs use site.storage.className. The bundled local-path chart is
  omitted when the customer supplies existing storage.
- Kamaji Helm hook RBAC/config are persistent resources. Setup jobs are Sync
  hooks at waves 21/31, retained for diagnosis until BeforeHookCreation replaces
  them on the next sync. Delete/teardown hooks and Helm test hooks are omitted.
- Certificate job uses portable shell redirection, exits on failure and refuses
  a partially existing certificate pair. cfssl init image is v1.6.5 (verified
  available), replacing the chart's hardcoded latest; the NVIDIA cfssl value
  alone does not affect that template.
- The etcd authentication job repairs partial setup: ensure root user, ensure
  root role, always grant it, enable authentication and inspect status. etcd
  v3.5.6 AuthEnable is idempotent when already enabled:
  https://github.com/etcd-io/etcd/blob/v3.5.6/server/auth/store.go
- MaintenanceOperatorConfig is wave 41, after its controller/webhook at 40.
- DPFOperatorConfig follows the Zero Trust or Host Trusted upstream template and
  receives customer inputs. argoCDNamespace is explicit. No physical inventory,
  BMC passwords, tenant addresses or BFB/service selections are copied from our lab.
- Argo CD bootstrap uses NVIDIA values plus annotation tracking to preserve Helm
  release labels. Argo bootstrap itself is a Helm release outside the Application.
- All other resources follow the pinned charts/values. Controller-created objects,
  runtime certificates and DPU service Applications are not pre-rendered here.

Kubernetes installer, production HA design, physical DPU onboarding bundle,

Optional tenant extension:
- DPF 26.4.0 DPUCluster API and bundled CRD schema:
  https://networking-docs.nvidia.com/dpf/26.4.0/dpucluster
- Same pinned NVIDIA source as above: internal/clustermanager/kamaji/handler.go
  confirms TenantControlPlanes use their DPUCluster name and namespace.
- Tenant resources use wave 70, after DPFOperatorConfig at wave 60. The shared
  controller/store remain in dpf-operator-system; tenant control planes have
  separate namespaces. Settings ship disabled with placeholder VIPs/interfaces.
- Site validation supports IPv4/keepalived, unique tenant names and VRRP IDs,
  and the DPUCluster maxNodes schema bound. It is not network/IPAM validation.

DSX OS external-Argo adaptation, 2026-10-16:
- Imported charts, values, base renderer and tests from kirson-git/openshell-dpu
  commit c5af6e9034d8cb407d973a0e483befccaf858b04.
- tools/external.py is the public rendering entrypoint. Its Application namespace
  is independent of the DPF service Argo namespace. The generated manifests include
  the service Argo; its Redis init hook uses persistent RBAC then a Sync Job.
- External Argo bootstrap owns Argo CRDs on a shared cluster; on separate clusters
  the service chart installs its own cluster's CRDs. Installation IDs and namespace
  watch scopes are distinct. Separate stage Applications sync manually; the
  one-file full-stack Application syncs automatically, without pruning.
- profiles/two-tenant-hbn models the observed lab root resources using illustrative
  addresses and hardware identities. It includes no live credentials or raw logs.

One-file/profile adaptation:
- install.yaml combines platform and profile sources into one Application. Global
  sync waves and scoped readiness Jobs gate operator reconciliation, tenant readiness
  and BMC Secret presence before hardware provisioning.
- credentials.sh supplies the private shared BMC password via Bash; temporary
  files are private, outside the checkout, and removed after use.
